# 二、我们的完整研究 IDEA

## 2.1 核心研究问题

我们关注一个可能被现有 Agent 自进化方法忽略的问题：

**一次经过验证的 Service 修复，能否为 Customer 提供有价值的信息，帮助它发现更多新的、合法的、可复现的 Service 弱点？**

普通 Agent 自进化是：

Service 执行任务 → 失败 → 反思 → 优化 → 再测试。

我们提出：

Customer 发现失败 → Service 修复 → 将真实修复证据反馈给 Customer → Customer 根据修复边界发现新的弱点 → Service 再修复。

重点不是两个模型简单轮流优化。

重点是：

**Repair Feedback 是否提供了相对于普通失败轨迹的额外搜索价值。**

## 2.2 两个角色

### Service

目标：

正确执行用户任务，遵守 Retail Policy，提高原生任务成功率。

优化对象：

一段始终可见的 Service 指导文本。

第一版禁止动态 Skill Activator。

让 GEPA 直接优化纯文本，不建立复杂 Skill JSON Schema。

### Customer

目标：

在保留原始 Retail 任务目标、事实和授权约束的情况下，探索不同的合法交互策略，发现 Service 的失败。

允许探索：

- 原场景允许的信息披露顺序
- 原场景允许的确认方式
- 多请求之间的交流顺序
- 合法的澄清与追问
- 合法的条件表达
- 已有目标之间的对话切换
- 其他未预先限定的交互机制

禁止：

- 新增原任务不存在的订单或商品
- 擅自改变购买、退款、换货目标
- 篡改预算和支付约束
- 编造后台数据
- 让 Customer 知道它不应该知道的工具结果
- 为了制造失败而擅自撤销任务
- 为了刷分而阻止任务正常完成
- 将任务目标从合法请求改成恶意越权请求
- 使用隐藏标准答案指导 Service

注意：

不能简单规定 Customer 必须在任何情况下都始终说真话。

某些原生任务本来就要求用户表达怀疑、隐瞒指定信息或按照场景要求纠正客服。

**是否忠实于原任务，应以当前任务明确的事实、目标和交互约束为准，而不是额外施加一条会与任务冲突的通用道德或真实性规则。**

合法挑战必须保持原任务约束，但允许场景本来授权的合理交互变化。

## 2.3 什么叫有效发现？

Customer 让 Service 得分降低，不自动等于发现弱点。

有效发现至少需要：

1. Customer 行为合法且符合原任务。
2. 真实 Customer–Service 对话实际发生。
3. 所声称的挑战确实暴露在对话中。
4. Service 出现可定位的失败。
5. 失败能够复现或具有相应的重复证据。
6. 失败不能只由任务目标被篡改造成。
7. 不把重复出现的同一种失败机制无限计数。

原生 Reward 必须保留。

同时，针对关键发现，记录原始工具调用、业务行为与对应政策证据。

Native Reward 不等于完整的政策合规判断。

不要为了让指标变好修改 Native Scorer。

## 2.4 Repair-Conditioned 的具体定义

当 Service 从 S0 修复为 S1 时，记录：

- S0 失败的真实轨迹。
- S0 与 S1 指导文本的变化。
- 已验证的行为差异。
- 修复在哪些任务条件下有效。
- 仍然不确定的修复边界。

将这些证据提供给 Customer Evolver。

Customer 自由提出：

- 可能仍然存在的残留失败。
- 可能由修复引发的回归。
- 修复信息提示的其他合法交互弱点。

不能预先只允许几个固定错误类别。

不能提供 H 测试集标准答案。

不能将修复描述为已有效，除非有对应真实评测证据。

## 2.5 两种关键对照

### Free-GEPA

Customer 看到：

- 相同的 E 任务历史。
- 相同的过去失败轨迹。
- 相同的可公开观察的交互证据。

但不看 Service 的修复文本差异及专门修复总结。

### RC-GEPA

Customer 获得同样的信息，另外获得：

- S0 → S1 的真实文本差异。
- 修复效果证据。
- 已观察到的修复边界。

两组使用：

- 同一个 Qwen3.7-Plus。
- 相同初始 Service 状态。
- 相同任务集合和 Seed 计划。
- 相同 GEPA 搜索设置。
- 相同候选评测预算。
- 相同合法性标准。
- 相同失败判定标准。

**两组主要实验变量必须是：是否获得真实 Repair Feedback。**

如果存在额外 Token 数量差异，报告上下文长度，并在预算允许时设置长度匹配的非修复信息对照。

## M1：GEPA-Service Baseline

固定原生 Customer。

使用 GEPA 搜索 Service 指导文本。

要求：

- 从无额外指导或固定初始指导开始。
- GEPA 根据真实失败轨迹优化文本。
- 多个真实不同的候选必须进入评测。
- 在 E 训练任务中提供反思信号。
- 使用 V 进行模型选择。
- 不使用 H 反馈优化。
- 保留 GEPA 官方优化结果和候选历史。

比较：

**Native Service vs GEPA-Optimized Service**

衡量：

- Native Accuracy。
- Pass^k（仅报告实际运行过的 k）。
- 每个候选的评测次数。
- E/V 上的有效提升。
- 独立测试的泛化表现。
- API 请求与 Token 成本。

如果 GEPA 生成了真实候选但最终没有正收益，必须如实记录。

不能通过修改 Retail 原生任务使其获得提升。

## M2：Free Customer Evolution

在 M1 建立的 Service 状态上，使用 GEPA 优化 Customer 交互策略。

Customer 不接收 Repair Feedback。

重点检查：

- 合法候选比例。
- 实际评测候选数量。
- 是否产生不同的交互压力。
- 是否发现新失败。
- 是否有真实任务失真。
- 是否只是重复原本已有的失败。

Customer 的优化奖励不能简单写成：

`1 - Native Reward`

否则可能鼓励制造任务失真。

至少需要区分：

- 候选合法性。
- 挑战是否真正暴露。
- 是否在原先成功的任务上产生新失败。
- 失败是否可复现。

无效挑战不能因为成功降低 Service 分数而获得正向收益。

## M3：Repair-Conditioned Customer Evolution

从 M1/M2 的真实、经过验证的 Service 改进中获取：

S0 → S1。

冻结这对 Service。

将修复前后的轨迹与文本差异构造成 Repair Feedback。

在相同 S1 上进行：

- Free-GEPA Customer 搜索。
- RC-GEPA Customer 搜索。

两组冻结相同的候选测试预算与评测任务。

记录：

- Customer 候选总数。
- 合法候选数量。
- 实际执行候选数量。
- 新失败发现数量。
- 可复现新失败数量。
- 不同失败机制数量。
- Fail→Fail 残留失败。
- Pass→Fail 潜在回归。
- 请求成本。

同一 task×seed 的自然对话可能因策略不同而分叉。

因此不能把同 Seed 自动理解为完全受控的逐消息配对试验。

需要结合重复实验和具体行为证据。

**这一阶段是整篇论文最重要的实验。**

## M4：完整交替进化

实现真正的多轮闭环：

1. 当前 Customer 测试当前 Service。
2. Service GEPA 根据失败改善策略。
3. 通过真实评测确认候选修复状态。
4. 产生修复反馈。
5. Customer GEPA 使用修复反馈提出挑战。
6. 对新挑战进行合法性与真实行为验证。
7. Service 继续优化。
8. 重复多个循环。

至少预设多个交替循环，而不是只演示一次 S0 → S1。

但循环数必须受固定总预算约束。

不得为了显示“持续提升”强迫每轮接受一个候选。

没有有效改进时，允许保持当前版本不变，并准确记录停滞。

不得将停滞伪装为一次成功进化。

### 两种完整闭环

A. Free Co-Evolution：Customer 不使用修复反馈。

B. Repair-Conditioned Co-Evolution：Customer 使用真实修复反馈。

两组从相同的冻结初始状态开始，使用可比的模型和预算。

注意：

多轮执行之后两个分支的 Service 状态可能不同。

因此：

- 固定同一 S1 的 Free vs RC 对照作为核心因果实验。
- 多轮交替进化作为进一步验证长期作用的实验。
- 不要将两个分支后期状态不同产生的所有差异都直接归因于单次 Repair Feedback。

# 五、数据划分与防泄漏

## 5.1 E / V / H

必须严格区分：

**E：Evolution**

用于候选优化、轨迹反思和训练中的搜索。

**V：Validation**

用于模型选择、候选比较和进化过程中必要的验证。

**H：Held-out Test**

只能在完整方法、超参数、对照与候选选择冻结后用于最终评测。

优先采用官方 Retail train/test split。

E 与 V 从官方 train 中划分。

H 从官方 test 中选取，优先覆盖完整测试集；如果官方分布或可用任务不足，应记录实际规模。

任务列表、Seed、划分算法和所有哈希应在正式搜索前写入不可变 Manifest。

必须检查与旧 EvoTau 已使用任务的重叠。历史上已经暴露过评测结果的任务不能无条件宣称为全新、从未观察的盲测任务。

## 5.2 H 的严格规则

- 不读取 H 任务正文辅助开发。
- 不在 H 上挑选模型。
- 不在 H 上选择 Prompt。
- 不根据 H 的得分重新修改算法。
- 不通过反复查询 H 选取最优实验版本。
- 不把 H 的标准答案放入反思数据。
- 不使用历史 H 成绩训练新策略。

方法冻结后统一执行最终 H。

如果发现真正的评分器实现 Bug，必须把评分协议变更记录为新的 Benchmark 版本，原结果保留，不能只修复对自己不利的案例。

## 5.3 多 Seed

正式实验必须采用多 Seed。

优先设计：

- 多个独立搜索重复。
- 同一批任务的多个仿真 Seed。
- H 上独立重复测试。

建议以至少 3 个独立搜索重复作为目标，并根据预算为最终 H 配置多次执行。

实际重复数由冻结的可行性与请求预算规划决定，不能声称没有运行的重复已经完成。

如果预算不足以完成预定统计功效，必须报告限制，而不是将一次运行描述为稳定结论。

# 七、主要科学指标

## 7.1 Primary Metric

核心指标定义为：

**Valid Novel Failure Discovery Rate**

即：

在相同 Customer 搜索与真实评测预算下，发现多少个合法、实际触发、可复现的新 Service 失败。

建议同时报告：

- 每 100 个实际评测候选发现的新失败数。
- 每 1,000 次真实 LLM 请求发现的新失败数。
- 新失败覆盖的独立 task 数量。
- 不同失败机制数量。

必须区分：

- Candidate 数量。
- Episode 数量。
- 独立 Task 数量。
- Task×Seed 单元数量。
- 独立失败机制数量。

这些分母不能混用。

## 7.2 Secondary Metrics

包括：

- Service Native Accuracy。
- H 上的 Accuracy Delta。
- Pass^k。
- Customer Validity Rate。
- Challenge Exposure Rate。
- Residual Failure Count。
- Possible Regression Count。
- Verified Regression Count。
- 后续 Service 修复成功数。
- 修复造成的任务退步数。
- API 请求数。
- Token 成本。
- 每项有效发现的请求成本。
- 不同演化代数的效果曲线。

## 7.3 评分可信性

原生 τ² Reward 作为基础结果。

如果声称发现新的政策违规，必须保留：

- 用户原始请求。
- 相关 Service 原文。
- 工具调用。
- 工具结果。
- 对应 Policy。
- 为什么属于错误的行为解释。

对关键发现进行独立于候选生成过程的证据复核。

可以使用离线确定性检查和必要的辅助审查。

不要因为增加一个复杂 LLM Validator 能让代码看起来更完整，就引入庞大的评审流水线。

自动审查结论必须标记为自动审查，不能冒充人工独立验证。

证据不足的案例归为 unresolved，不能强行计作有效发现。

## 7.4 统计分析

提前定义主要比较：

**Open-RC vs Free-GEPA。**

优先使用按任务分组、考虑 Seed 重复的置信区间或 Bootstrap 方法。

记录：

- 效果量。
- 95% 置信区间。
- 独立重复数。
- 任务数量。
- 置信区间的统计单位。
- 多重比较处理方式。
- 是否包含零效果。

不能把同一个任务上反复产生的 episodes 当成相互独立的任务样本。

如果样本量不足，报告探索性结果，不伪称统计显著。

不能事后挑选效果最好的 Seed 作为主实验。

# 八、工程设计与质量控制

## 8.1 测试先行

在启动大规模 API 请求之前，必须拥有：

- GEPA Adapter 单元测试。
- Retail 原生运行集成测试。
- Prompt Overlay 隔离测试。
- E/V/H 不重叠测试。
- H 数据禁止参与搜索的测试。
- 预算并发计数测试。
- 超额预算拒绝测试。
- 运行中断与恢复测试。
- 评分保真测试。
- Customer 非法挑战处理测试。
- 修复反馈正确归属测试。
- Free/RC 信息隔离测试。
- 结果统计与图表生成测试。

Mock 测试只能证明接口工作，不能被当成真实实验成绩。

## 8.2 自动修复纪律

遇到错误时：

1. 先获得最小复现。
2. 确认是工程 Bug、模型输出问题、Benchmark 问题还是研究假设不成立。
3. 只修复对应层次的问题。
4. 添加回归测试。
5. 重新验证受影响的结果。
6. 保留失败证据。

禁止采用：

“发现一个模型输出格式错误 → 新增三个恢复模块 → 再新增多个 Validator → 再新增特殊 Gate”

这种层层叠加的方案。

如果使用官方 GEPA 原生文本接口即可解决，就不要引入自定义多层 JSON Schema。

## 8.3 禁止的架构行为

不得新增：

- 第二套 GEPA 搜索器。
- 无必要的任务队列服务。
- 大规模分布式调度框架。
- 自定义数据库平台。
- 通用插件系统。
- 多层 Agent Manager。
- 复杂 Skill Registry。
- 旧 EvoTau 的兼容模式。
- 与核心假设无关的多模型路由。
- 无实际实验依据的候选评审机制。
- 为通过某个冻结 Benchmark Task 而编写的专用提示答案。

如果某个新增模块不能通过一句话说清：

“它解决哪个已经证实的问题，为什么官方能力不能解决？”

就不应该增加。

## 8.4 版本与可恢复性

要求：

- 固定依赖。
- 固定 Git revision。
- 固定配置。
- 记录运行 ID。
- 记录每个候选 Prompt 及哈希。
- 记录真实评分与轨迹。
- 记录完整 API 使用量。
- 支持从中断继续。
- 不重复计费已经完成的 episode。
- 缓存键包含任务、Seed、Prompt、模型、环境与评分版本。
- 禁止不同实验条件错误共享缓存。
- 每次独立实验使用独立输出目录。
- 中断恢复不得改变原冻结协议。

如果发现结果缓存错误，应作废受污染的实验结果，不能静默保留。

# 十二、如何防止再次形成屎山？

本部分拥有最高工程优先级。

## 12.1 一次性完成，不代表一次性堆完所有抽象

先确定完整架构和全部研究接口，然后在同一次任务中依序实现、测试、运行。

不需要用户逐阶段批准。

但不要在第一天写出整个复杂框架后才第一次测试。

内部执行顺序应当是：

架构冻结 → GEPA/τ² 联调 → Service → Customer → Repair Feedback → 完整交替 → 统计 → 最终验收。

每完成一个子系统就运行相应测试，发现问题就定位并修复当前实现。

## 12.2 只允许研究驱动的复杂度

新增运行时功能必须满足至少一个条件：

1. 是执行完整 Open-RC 所必需。
2. 是公平比较 Free vs RC 所必需。
3. 是阻止真实数据泄漏或预算失控所必需。
4. 是真实可复现性所必需。

其他需求一律不作为框架功能加入。

## 12.3 失败时优先删除复杂度

如果某个组件频繁失败：

首先检查是否可以直接使用官方 GEPA 或 τ² 功能替代。

如果可以，删除该组件。

不要默认继续堆重试、修复器和审核器。

## 12.4 不允许为了保护旧设计牺牲新系统

这是一个新仓库。

不需要迁移历史框架。

不需要兼容旧 Skill Schema。

不需要复现旧晋升流程。

不需要保持过去的所有抽象接口。

我们要的是新的科研实验装置，不是一个通用自进化产品平台。
